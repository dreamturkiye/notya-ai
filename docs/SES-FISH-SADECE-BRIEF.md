## What must change: the listening layer
Fish Audio has no live-streaming ASR. It has a file-based endpoint: `POST /v1/asr` (send an audio file, get back `text`, `duration`, timestamped `segments` — see Fish's docs at docs.fish.audio/features/speech-to-text, re-verify against their current docs, do not assume the shape from memory). Replace Deepgram Live entirely with:

1. **Local voice-activity detection (VAD), no vendor.** The existing barge-in code in `fishOturumu.ts`/`fishTarayici.ts` already does local RMS/energy-based speech detection for interrupting Fish's own playback — reuse the SAME technique for turn-taking on the doctor's side: buffer captured PCM while energy is above a speech threshold, and treat ~400–600 ms of sustained low energy after speech as end-of-utterance (name the constant, make it tunable — this is the direct analog of Deepgram's `endpointing`/`utterance_end_ms` you designed before, just computed client-side instead of by a vendor).
2. **One utterance → one Fish ASR call.** When VAD declares the utterance finished, encode the buffered PCM as a WAV (or whatever format Fish's `/v1/asr` accepts — check current docs) and POST it through a new server route (`app/api/asistan/fish-dinle/route.ts` or similar — auth-gated like `fish-ses/route.ts`, forwards to `https://api.fish.audio/v1/asr` with the Fish key, key never reaches the browser) to get the transcript. The returned text becomes the ONE turn dispatched through the existing `turKilidi`/`sesTuru`/`fish-tur` single-dispatch path — this part is unchanged from `3ee3386e`, it does not care where the text came from.
3. **No dispatch on partial buffers.** Only a VAD-declared finished utterance is sent to `/v1/asr` — do not call Fish's ASR repeatedly on a growing buffer (that would be wasteful and reintroduce a version of the interim/final duplicate-dispatch bug from earlier today). One utterance, one ASR call, one model dispatch.
4. **Latency is the headline metric.** This design has a real, measurable latency cost the old streaming-ASR design didn't: end-of-speech → VAD confirms silence (~400-600ms by design) → upload+transcribe (network round trip + Fish's ASR processing time) → model dispatch → first Fish TTS audio. Log each stage's duration server-side (extend the existing usage-logging pattern) so this can be measured precisely, not estimated. Kaan's bar: this must feel like natural human back-and-forth, not a slow round-trip. If the ASR upload+transcribe step is consistently adding more than ~1s, say so plainly in the report rather than shipping it quietly — this is the single most important thing to be honest about.
5. **Turkish quality is unverified — this is what the test is for.** Do not assume Fish's `/v1/asr` handles Turkish medical speech well. Note in the report whatever signal you can get (does the API even accept a `language` parameter for Turkish? check current docs) but the real verdict needs a human test.
